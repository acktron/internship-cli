internship-radar

A command-line LinkedIn lead finder built around a persistent Playwright Chromium profile, defensive extraction, and layered relevance gates. This page documents the implementation in this repository.

Operational boundary: the README warns that automated scraping violates LinkedIn’s User Agreement. .linkedin-profile/ contains live session cookies and must not be committed or shared.

1. Overview

The package installs internship-radar = internship_cli.cli:main. It launches Playwright with a persistent Chromium user-data directory, defaulting to .linkedin-profile/. A user signs in and completes 2FA in the actual browser; the program only detects authenticated state and never reads, asks for, or stores a password.

login

Opens visible Chromium and guides manual login; session state persists in the profile.

search

Uses the LinkedIn Jobs tab; extracts structured job cards across result pages.

posts main

Uses content search, expands posts, filters genuine recent hiring leads, and can label companies.

company-posts

Runs several target-company content queries and keeps strict, concrete internship openings.

agent

LLM-driven wrapper around two bounded scraper tools, not unrestricted browser control.

2. Data flow

1 · CLIClick parses options; project .env is loaded.
2 · SessionPersistent Chromium opens and login status is checked.
3 · SearchJobs tab or LinkedIn content search is navigated.
4 · ExtractSelectors, scroll, expansion, field extraction, dedupe.
5 · FilterDate, terms, source legitimacy, company opening, links.
6 · Optional LLMCompany classification or agent relevance gate.
7 · WriteJSON, CSV, Markdown, or plain-text output plus metadata.

Broad posts first run deterministic filters. An allowlist is applied before permalink resolution. Company-first mode reuses content extraction, then adds proximity and organization/source checks. In agent mode the browser is opened only for a tool call and closed before LLM summarization.

3. File-by-file

cli.py

Purpose: Click commands and process lifecycle.

Key functions: main, login, search, posts, company_posts, agent.

Connection: creates browser contexts, builds HiringMatcher, calls scraper/agent paths, handles errors and sends records to write_results.

browser.py

Purpose: persistent Chromium and login boundary.

Key functions: persistent_context, is_logged_in, ensure_logged_in, profile_hint.

I/O: profile directory → Playwright context/page. It launches a persistent profile, grants best-effort clipboard permissions, recognizes login-wall URLs and authenticated navigation selectors.

scraper.py

Purpose: Jobs-tab scraper.

Key functions: build_search_url, _scroll_results, _extract_cards, scrape_jobs; output dataclass Job.

I/O: query/options → list[Job]. It adds location/remote/time facets, tries selector fallbacks, removes tracking from job URLs and deduplicates by job ID.

posts.py

Purpose: content-search engine plus company-query orchestration.

Key functions: build_content_url, _load_more, _expand_see_more, _extract_post, scrape_posts, resolve_post_links, default_company_queries, search_company_internship_posts.

I/O: broad search → (list[Post], stats, search_url); company mode → result dictionaries plus totals. It extracts post/header/job-card fields, applies filters/gates, and resolves exact post URLs from anchors, embed dialog or Copy link.

filters.py

Purpose: deterministic relevance and source legitimacy.

Key functions: parse_relative_date, parse_datetime_attr, HiringMatcher.match, match_strong_company, extract_funding_mentions, load_allowlist, classify_first_party.

Connection: parses compact/verbose LinkedIn dates, matches bounded term groups, enforces company proximity and job-offer cues, and detects aggregators/spam.

links.py

Purpose: outbound URL extraction, redirect resolution and apply-link classification.

Key functions: extract_urls_from_text, RedirectResolver.resolve, classify_final_url, classify_links.

Connection: cached/throttled HEAD→GET handling recognizes ATS/careers URLs and rejects chat, community, invite and link-hub destinations.

gate.py

Purpose: batched LLM relevance/source gate for agent results.

Key functions: gate_hiring_posts, _parse_verdicts, normalize_agent_row, format_result_blocks.

I/O: candidate dictionaries → kept/enriched dictionaries. It requires JSON, ranks company/employee/recruiter/creator hits, and fails open if the LLM response fails.

llm.py

Purpose: shared Gemini/Ollama backend layer.

Key functions: load_project_env, get_backend, get_llm_client, GeminiClient.complete, OllamaClient.complete.

Connection: normalizes Message, ToolCall and Completion. Gemini uses GEMINI_API_KEY; Ollama uses local localhost:11434/v1, a 120-second timeout and one retry.

classify.py

Purpose: optional, unverified company categorization.

Key functions: CompanyClassifier.classify, Classification.label, is_startup.

I/O: names → cached classifications with category, confidence, <backend>-guess and verified: false. Only funded_startup passes --llm-filter.

agent.py

Purpose: bounded LLM tool-calling search loop.

Key functions: make_browser_factory, AgentRuntime.execute, AgentRuntime._scrape_posts, AgentRuntime._company_posts, Agent.run, build_agent.

Connection: exposes only scrape_posts and company_posts; it clamps tool arguments, invokes the relevance gate and returns compact rows to the LLM loop.

output.py

Purpose: format inference and serializers.

Key functions: infer_format, make_snippet, write_results.

Connection: accepts dataclasses or mappings. JSON is a metadata envelope; CSV uses fields; Markdown uses tables; TXT produces numbered blocks and optional company grouping.

debug.py

Purpose: selector-drift diagnostics.

Key functions: count_candidates, dump_debug, page-side _DISCOVERY_JS.

I/O: page + selector groups → DOM, screenshot, and report. It counts candidate selectors and surfaces activity-URN carriers, attributes, classes and HTML samples.

4. Key decisions

Layered false-positive control

Search terms only yield candidates. Recency, term groups, source legitimacy, links, and company-opening checks distinguish “I did an internship at X” from “X is hiring.”

Word-boundary terms

HiringMatcher compiles boundary-aware regexes so ml does not match “html” and ai does not match incidental substrings.

Three funding layers

1) quote funding mentions in post text; 2) deterministic normalized-company allowlist; 3) optional LLM triage. The allowlist is the defensible filter; LLM labels are guesses.

SDUI resilience

Content search has unstable hashed classes. Extraction uses data/ARIA/component hooks with legacy fallbacks; debug discovery finds activity-URN-bearing elements when known selectors break.

Exact permalink hygiene

Search and company-page URLs are not considered post permalinks. The resolver prefers valid timestamp/card anchors, embed HTML, then Copy link; results are cached and invalid pseudo-URLs cleared.

Capped agent design

The LLM gets two local tools, not arbitrary browsing. Argument normalization and agent limits bound tool calls, companies, query variations, results, scroll depth, and delays.

5. Output schemas

Jobs: search

{ "query": "…", "location": "…", "scraped_at": "ISO-8601", "count": 0, "results": [{"company":"…","title":"…","location":"…","link":"…"}] }

Posts: posts

{ "query":"…", "max_age_days":14, "match_mode":"all", "count":0, "results":[{"poster":"…","company":"…","role":"…","location":"…", "post_date":"…","job_link":"…","why_matched":"…","funding_signal":"…", "company_class":"…","post_url":"…","source_type":"…","link_class":"…"}] }

Company / agent rows

company-posts: company, poster, snippet, post_url, why_matched, source_type agent: company, role, why_matched, post_url, source_type

JSON always includes metadata, scraped_at, count, and results. CSV writes selected fields; Markdown turns link fields into [open](URL); TXT uses compact blocks, optionally grouped by company.

Tests and packaging

pyproject.toml uses Hatchling and declares Playwright, Click, and python-dotenv. The tests cover hiring and strict-company matching, query generation, see-more expansion, source/LLM gate behavior, link resolution, post permalink resolution, Gemini/Ollama behavior, and agent browser cleanup/tool caps. Fixture HTML represents activity and reshare cards.

For extraction maintenance, add a focused fixture/test, then run posts --debug against the changed LinkedIn surface. The debug report is designed to reveal selector counts and activity-URN structural anchors.
